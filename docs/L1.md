# KYA-OS Level 1 Walkthrough — Agent Identity

**L1 (Agent):** the agent has a stable DID and can prove control of it.
Delegation is optional at this level. This doc traces the L1 flow through the
code, citing `file:line`, the requirement it satisfies
([`REQUIREMENTS.md`](./conformance/REQUIREMENTS.md)), and the proving test
([`CONFORMANCE.md`](./conformance/CONFORMANCE.md)).

> Line numbers are accurate as of writing; if they drift, the `// KYA-OS R-Lx-n`
> comment at each site is the stable anchor.

## The L1 story

An agent is named by a DID. Before anyone trusts a request, the agent proves it
controls that DID by signing a fresh nonce challenge — no key material ever
crosses the wire. The verifier resolves the DID to a public key and checks the
signature and the challenge's freshness.

## 1. The agent has a DID (R-L1-1)

Identity is a DID; the challenge token carries the `agentDid` it is issued to.

- **Code:** `mcp-server/lib/core/challenge.js:28` (`generateChallenge`),
  file overview at `challenge.js:4`.
- **Test:** `challenge.test.js` → `creates a token with the given agentDid`.

## 2. did:key resolves offline (R-L1-2)

A `did:key` encodes its public key in the identifier itself, so resolution is
deterministic and needs no network. This keeps the auth path fast and testable.

- **Code:** `mcp-server/lib/tools/didKeyContext.js:100` (`resolveAgentKey`),
  citation at `didKeyContext.js:94`.
- **Test:** `resolveAgentKey.test.js` →
  `resolves a did:key offline without the network resolver`.

## 3. Other DID methods resolve appropriately (R-L1-3, R-L1-4)

Non-`did:key` DIDs resolve by method: `did:web` natively (fetch the host's
`did.json`), everything else via the Universal Resolver. `did:web` falls back to
the Universal Resolver if the direct fetch fails.

- **Code:** `mcp-server/lib/core/resolver.js:45` (`resolveDID`), citation at
  `resolver.js:48`; the pure URL transform in `lib/core/didWeb.js`.
- **Tests:** `resolver.test.js` →
  `resolves did:web by fetching .well-known/did.json directly`,
  `falls back to the Universal Resolver when did:web fetch is non-2xx`;
  `didWeb.test.js` → `maps a bare domain to its .well-known URL`.

## 4. The agent proves control of its DID (R-L1-5)

The agent signs `signingInput(token)` (the nonce, agent DID, and issuance time)
with its private key. The verifier checks that signature against the public key
resolved in step 2/3. No private key is transmitted.

- **Code:** `mcp-server/lib/core/challenge.js:38` (`signingInput`),
  `challenge.js:61` (`verifyChallengeResponse`); invoked in the delegation flow
  at `lib/tools/delegate.js:54` (step 0).
- **Tests:** `challenge.test.js` →
  `returns valid for correct signature within TTL`; `delegate.test.js` →
  `authorizes when authProof is valid`.

## 5. Expired or forged challenges are rejected (R-L1-6)

A challenge past its `expiresAt`, or a signature from the wrong key, fails
closed.

- **Code:** `mcp-server/lib/core/challenge.js:49` (`isChallengeExpired`),
  `challenge.js:61` (`verifyChallengeResponse`); enforced at
  `delegate.js:55` (the R-L1-5/R-L1-6 citation).
- **Tests:** `challenge.test.js` → `returns invalid for expired token`,
  `returns invalid for wrong key`; `delegate.test.js` →
  `denies when authProof challenge is expired`,
  `denies when authProof signature is wrong`.

## Where L1 fits

L1 establishes *who the agent is*. On its own it answers "is this a real agent
that controls its DID?" — not "may this agent do X for a user." That second
question is **L2**, which builds a user-issued credential and a per-request
authorization check on top of this identity. See [`L2.md`](./L2.md).
