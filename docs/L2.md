# KYA-OS Level 2 Walkthrough — User-to-Agent Delegation

**L2 (Agent + User):** both the user and the agent have DIDs. The user issues a
Verifiable Credential to the agent, and every request is verified at the edge —
proof, issuer, expiry, revocation, and scoped access. This doc traces the L2
flow through the code, citing `file:line`, the requirement
([`REQUIREMENTS.md`](./conformance/REQUIREMENTS.md)), and the proving test
([`CONFORMANCE.md`](./conformance/CONFORMANCE.md)).

> Line numbers are accurate as of writing; if they drift, the `// KYA-OS R-Lx-n`
> comment at each site is the stable anchor.

## The L2 story

The user issues the agent a VC 2.0 credential — an eddsa-rdfc-2022 Data
Integrity proof binding claims to the agent's DID. When the agent later requests
an action, the resource server runs `check_delegation`: a single, ordered,
fail-closed pipeline that re-verifies everything per request. The LLM never
decides — it relays this pipeline's structured verdict.

## Issuance — the user creates the delegation (R-L2-1)

The user issues a VC with the agent as `credentialSubject.id` and the permitted
claims/scope embedded.

- **Code:** `mcp-server/lib/core/vc.js:101` (`issueCredentialDI`), citation at
  `vc.js:95`; tool entry `lib/tools/issue.js:36` (`issueCredentialTool`).
- **Test:** `vcDataIntegrity.test.js` →
  `issues a VC 2.0 with an eddsa-rdfc-2022 proof`.

## The per-request pipeline — `check_delegation`

`mcp-server/lib/tools/delegate.js:49` (`checkDelegation`). The numbered steps
below map 1:1 to the comments in that function and run in order, each returning
a denial reason on failure.

### Step 0 — agent authentication (R-L1-5, R-L1-6)

If an `authProof` is supplied, the L1 challenge check runs first (see
[`L1.md`](./L1.md) steps 4–5).

- **Code:** `delegate.js:54`.
- **Tests:** `delegate.test.js` → `authorizes when authProof is valid`,
  `denies when authProof challenge is expired`.

### Step 1 — credential is bound to this agent (R-L2-2)

`credentialSubject.id` MUST equal the requesting agent DID, so one agent cannot
present another's credential.

- **Code:** `delegate.js:85`.
- **Test:** `delegate.test.js` → `denies when VC subject does not match agent
  DID`.

### Step 2 — proof, issuer, and validity window (R-L2-3, R-L2-4, R-L2-5, R-L2-6)

The Data Integrity proof MUST verify against the issuer DID resolved by the
document loader, and the credential MUST be within its validity window — neither
expired (`validUntil`) nor not-yet-valid (`validFrom`).

- **Code:** `delegate.js:96` (calls `verifyCredentialDI`); the verification
  itself at `lib/core/vc.js:134`, citation at `vc.js:139`.
- **Tests:** `vcDataIntegrity.test.js` → `rejects a tampered credentialSubject`,
  `rejects a credential signed by a different key`, `rejects an expired
  credential`, `rejects a not-yet-valid credential`; `delegate.test.js` →
  `denies when the issuer is swapped to an unrelated DID`,
  `denies when VC is expired`, `denies when VC is not yet valid`.

### Step 3 — revocation (R-L2-7, R-L2-8)

If the credential carries a `credentialStatus`, the status list is fetched and
the credential's bit checked per request. A revoked credential is denied. The
StatusList2021 codec is DB-compatible (base64url + gzip, MSB-first).

- **Code:** `delegate.js:109` (step 3); status decode at
  `lib/core/revocation.js:58` (`checkRevocationStatus`), citation at
  `revocation.js:13`.
- **Tests:** `revocation.test.js` → `returns revoked when bit set`,
  `decodes a gzip+base64url encoded status list`.

### Step 4 — scoped access (R-L2-9, R-L2-10)

The requested action's required claims MUST be satisfied by the credential.
Predicates (`$gte`, `$in`, …) express scope, and numeric operators never coerce
— a string `"25"` cannot pass `{$gte: 21}`.

- **Code:** `delegate.js:130` (step 4); the engine at
  `lib/core/claimPredicates.js:41` (`evaluatePredicate`), no-coerce guard at
  `claimPredicates.js:48`, and `claimPredicates.js:118` (`checkClaims`).
- **Tests:** `delegate.test.js` →
  `authorizes when predicate $gte is satisfied`,
  `denies when required claim is missing from VC`; `claimPredicates.test.js` →
  `numeric-looking string fails $gte`, `boolean true fails $gt (no coercion to
  1)`.

## Multi-hop delegation chains (R-L2-11, R-L2-12)

When authority is delegated through intermediaries, the chain MUST verify
cryptographically from a root capability down to the leaf agent, enforcing
expiry attenuation (a child cannot outlive its parent) and rejecting a
scope/target/root mismatch. Built on `@digitalbazaar/zcap`.

- **Code:** `mcp-server/lib/tools/verifyChain.js:48`
  (`verifyDelegationChainTool`); leaf-controller check + citation at
  `verifyChain.js:56` (R-L2-11), chain verification at `verifyChain.js:67`
  (R-L2-12).
- **Tests:** `verifyChain.test.js` → `authorizes a valid 2-hop chain`,
  `authorizes a valid 3-hop chain`, `denies a delegation whose expiry was
  extended`, `denies when the root capability does not match`.

## Cross-cutting guarantees

These hold across the L2 flow:

- **The LLM is never the authority (R-X-1).** The demo agent derives its verdict
  from the `check_delegation` tool result, not its own prose.
  `demo-agent/lib/agent.js:51` (`decisionFromTool`), citation at `agent.js:12`.
  Test: `agent.test.js` → `canary: denies a verdict reached WITHOUT calling the
  tool`.
- **No secret leakage (R-X-2).** No key material appears in agent output or
  tool-call arguments. Test: `agent.test.js` → `never leaks the sentinel secret
  in output or tool args`.
- **Offline document loader (R-X-3).** `@context` resolves with no network IO on
  the hot path. `mcp-server/lib/core/documentLoader.js:84`
  (`createDocumentLoader`), citation at `documentLoader.js:13`. Test:
  `documentLoader.test.js` → `serves the agent credential context offline`.

## Where L2 stops

L2 covers the full user→agent delegation lifecycle with per-request edge
verification. It does **not** include selective disclosure (proving `over_21`
without revealing the rest of the credential) or credential-to-token bridging —
those are **L3 / Phase 2** (`ecdsa-sd-2023`, ECDSA keys). See the out-of-scope
rows in [`REQUIREMENTS.md`](./conformance/REQUIREMENTS.md).
